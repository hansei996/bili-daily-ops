# bili-daily-ops

> 让一个 B站账号**持续日更**，并且每次都比上次更清楚为什么有效。
> 不生成视频，只做**判断**：今天该拍什么、这条能不能进流水线、这周退步退在哪一环。

## 一条命令看清它现在能干什么

```bash
python tools/status.py
```

## 为什么先做「守门 + 库存」，而不是「选题生成」

日更最容易断在 **S0「当天定题」**：它是唯一**没有降级品**的一站
（剪辑能砍特效、审核能用兜底稿，选题砸了只能交零），而且「今天不做也不会立刻疼」，
于是决策被推到一天里最贵的时候 —— 晚开工 → 降质 → 数据差 → 更不想做，是断更的复利循环。

所以第一件事不是「多给你几个点子」，是**判这条能不能进库、库还够不够 7 天**。

> 每天做什么、每周看哪张表、判「退步」时按什么顺序查：见 [`docs/DAILY-WORKFLOW.md`](./docs/DAILY-WORKFLOW.md)。

## 五个工具，一条链路

| 环节 | 命令 | 它拒绝什么 |
|---|---|---|
| 选题准入 | `python tools/topic_gate.py check topics.jsonl` | 三行不齐 / 不可证伪 / 说不出差异化 / 只会复述常识 |
| 库存水位 | `python tools/topic_gate.py backlog topics.jsonl --days 7` | 库存低于 7 天时喊停（今天第一件事是补库，不是拍片） |
| 记录口径 | `python tools/validate_run.py runs/` | 百分数混进比例字段、完播比时长还长、metrics 在 publish 之前 |
| 退步判定 | `python tools/cohort_check.py runs/ --cohort X` | **样本不足时不许说「无退步」** |
| 周总账 | `python tools/daily_check.py runs/ --week A..B --assert ...` | 退出码只有 0 全过 / 1 硬断言失败 / 2 输入不合法 |

## 一张周表说清一周

```bash
$ python tools/daily_check.py examples/two-weeks --week 2026-10-19..2026-10-25 --assert "cohort:completion"
日期          准入   发布  完播   CTR   cohort  判定
2026-10-21  3/3  有   46%  5.0%  OK      2026-10-21-run
2026-10-22  3/3  有   24%  5.0%  低       2026-10-22-run
2026-10-23  3/3  有   22%  5.0%  低       2026-10-23-run

FAIL  cohort:completion   退步（本窗口可判定最小退步 30%）
结果：1 条断言失败（周区间 2026-10-19..2026-10-25）     ← exit 1
```

注意最后那行：**它同时告诉你「判出来了」和「这个判定能看多细」**。
没有「本窗口可判定的最小退步」这一行的看板，就是在假装精确。

## 一个必须先讲清的数字：7 天不够看「退」

| 事实 | 数值 |
|---|---|
| n=7 全对的 Wilson 95% 下界 | 0.6457 → 只排除 35.4% 的失败率 |
| 90% → 70% 的退步要多少条才看得见 | 25 条（3.6 周） |
| 90% → 50%（崩） | 8 条 |

所以这个项目**不做日更回归看板**，改做同题材 cohort + 预注册规则（连续 3 条 < 基线阈值，全年误报 0.36 次）。
详见 `DECISION-D1-cohort.md`。

## 它什么时候该被关掉

写在 `DECISION-D2-positioning.md` 里，三条任一成立就停止加功能：

1. 4 周内没人用它记录满 7 天
2. 真实使用后判定与作者自己的判断 80% 以上冲突
3. 接口改签名导致取数成本 > 10 分钟/条

## 边界（不做的事）

- 不碰账号登录、不自动发布、不做刷量
- 不拿「确定性回放」当卖点 —— 平台是黑箱，封面不可能重放两次
- 不承诺播放量；只承诺判断有据、缺证据时不下结论
